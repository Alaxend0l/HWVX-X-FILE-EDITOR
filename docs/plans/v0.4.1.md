# HWVX-SDL 0.4.1 plan

Three features, after 0.4: device-matched button prompts, sharper fonts, and car stats that fit the physics.
Research only so far (read-only); stages are sized for one agent each. Tools are Rust (`xdlrs`), never Python.

## A. Button prompts that match the device

**Where the glyphs are.** One 128×128 atlas of 32 px cells (GC: A green, B red, X/Y kidneys, Z, L/R, Start,
d-pad, sticks): HW_IPack `interface_3:24`, `_5:3`, `_6:41`, `_7:41`, `_8:25` (RGBA8, byte-identical) and in world
packs as CMPR (index varies, e.g. `ch1_l8` 11). The pad picture: `_6/_7:124,125` and world 12/13. Interfaces use
only three cells: **A** (32,64), **B** (32,96), **X** (0,64). The PC's atlas (`interface_3:24`, `_6/_7:6`, DXT5)
holds keycaps in the same cells. Fonts hold no button characters: prompts are text with a gap plus an image.

**Meaning** (src/port/pad.c, src/game/Port_Keyboard.c): A = confirm (SDL SOUTH, Enter), B = back (EAST, Escape),
X = details (WEST, X). SDL buttons are positional, so the glyph comes from `SDL_GetGamepadButtonLabel`, not the pad
type (a Switch pad's confirm is labelled B).

**A0, a probable bug today:** pad.c maps EAST → B and WEST → X; on `SDL_GAMEPAD_TYPE_GAMECUBE` EAST is the physical
X, so GC B and X are likely swapped. Fix: map by label for that type (check on a real adapter).

**Design.** Per-port last-used device in pad.c (`Port_PromptStyle(port)`: ORIGINAL, XBOX, PS, SWITCH, KEYBOARD;
change only on a press). Swap at draw time: `rect->tex = Port_PromptTexture(obj->texture, player)` in
`InterfaceManager_DrawObject_Standard_Image`, the player from the rendering interface. Atlases recognised by
content at `DataPack_RefreshTextures` (works for every world, release and mixed build); replacements are
game-owned 512×512 RGBA8 (GC format 1, not the port's PC format) textures with the same cell layout, unused cells
copied from the original. Setting: launcher row "Button prompts: Auto / Original / Xbox / PlayStation / Switch /
Keyboard" (`graphics.cfg prompts=`, `HWVX_PROMPTS`, `--prompts`); tests pin `HWVX_PROMPTS=original`.

**Assets.** "The Meritite Union's Input Prompts 2.0.0", CC0 1.0, https://github.com/meritite-union/input-prompts.
About 20 PNGs from `png_256` (Xbox a/b/x/y, PS cross/circle/square/triangle, Switch a/b/x/y, keyboard
enter/escape/x) in `assets/prompts/src/` with a provenance README; `xdlrs prompts build/check` makes
`prompts.bin`, embedded like the ultimate recipe (≤ 1.5 MB). `thirdparty/` stays out of git.

**Controller page → the PC's remap screen** (user's idea). GC (and likely PS2) have no remapping: fixed layouts
only (`g_keyBinding`: built-in schemes; `PlayerHuman_SetDefaultControls`/`SetControlBinding`), and the controller
page shows the chosen layout on a GC pad picture. The PC has a keyboard remap screen (`0x434310`); on GC that slot
is an empty stub. Plan: decompile the PC's screen into the port, driven by the port's bindings (keyboard keys and
SDL pad buttons, saved in the pref dir), glyphs from the prompt system. Its interface objects are in the PC's
HW_IPack: shown as is with PC data or an ultimate build with the PC copy; on GC/PS2-only data fall back to a
launcher remap UI or the current page. To check: the PS2 side (HWVX-ALL-Decomp).

**Stages.** A0 GC mapping fix · A1 inventory (every atlas copy, cell use, PS2 glyphs, "(A) CONTINUE" source) ·
A2 assets and build step · A3 device tracking and setting · A4 recognition and draw-time swap (screenshots per
style; 4:3 demo identical with `original`) · A5 launcher row (N choices) · A6 the PC remap screen in place of the controller page (decomp of `0x434310`, bindings saved, fallback for GC/PS2-only data), docs.

## B. Sharper fonts

**How fonts work.** `Gfx_FontManager_AddFont` lays cells on a grid; UVs are fractions of the page, spacing only
advances. So a higher-resolution page can replace the pixels if the texture keeps its logical size: a GX-level
override (`GX_TexOverrideSet(image, pixels)` in gx_tex.c) leaves every layout table untouched. Pages are the same
glyphs on GC, PC and PS2 (the mix already takes the PC's cleaner copies), so one sharp set fits all.

**Known typefaces (from the user, 2026-11-13):** **Serpentine Sans** and **Samba is Dead** are two of the game's
fonts. B2 confirms which pages each one drew (render and compare) and checks each font's actual licence and
source before anything ships; the rest of the pages are still matched by shape.

**Decided (user, 2026-11-13):** Samba is Dead (G3 16×16, G4 32×30) ships (its licence allows redistribution, not
sale). Serpentine Sans (G9 24×32, commercial Monotype) is replaced by an **open lookalike the user approves** from
side-by-side samples. B1 inventory done (`xdlrs fonts list`, docs-pending/fonts-inventory.md).

**Stages.** B1 inventory (`xdlrs fonts list`: every page, cells, letters, where used; classify flat/tinted vs
baked effects) · B2 typeface matching (`xdlrs fonts match`: rasterise candidates with a Rust rasteriser, score
glyph masks; candidates to test: Eurostile/Microgramma, Bank Gothic, Neuropol, Square 721, Handel Gothic, DIN,
LCD/segment faces; open lookalikes: Michroma, Orbitron, Audiowide, Saira, Exo 2, Russo One, Oxanium, DSEG) - **the
user approves each typeface** · B3 GX override registry (proved with a 2× resampled page) · B4 page builder for
one approved open typeface · B5 the others · B6 optional bring-your-own font (vendored stb_truetype) · B7 launcher
row "Fonts: Original | Sharp" (default Original), docs.

Licensing: open fonts ship with provenance; commercial ones need an approved open lookalike or a player-supplied
font. Risks: baked effects, custom faces with no source, accents (F/G letter sets), GPU memory (~110 MB if all
pages are resident at 1024²).

## C. Car stats that fit the physics

**Where the bars come from.** `CarAHud.stats[4]` (u8, in each car's pack; prototype cars carry their own) →
`GSI_VehicleSelectionInfo` → roles 70-73 in InterfaceManager, used as the bar's animation time (the curve is in
the car-select interface data). Labels in HW_IPack interface_3: ARMOR, SPEED, STUNT, GRIP (role mapping to
confirm).

**Physics behind each.** SPEED: torque curve, maxRpm, gears, driveRpmScale, brakes, turbo, mass. GRIP: gripScale,
wheels, steerRate, tractionLift, and the PC's handling mode 2. ARMOR: maxHealth, damageThreshold, damageScale,
damagePercent/Level, mass. STUNT: pitch/roll/spin rates, maxTime, score and turbo yield, air control.

**Derive.** Compute ARMOR and STUNT; measure SPEED (drag runs: 0-50/100/150, top speed) and GRIP (skidpad lateral
g, slalom) with `HWVX_DETERMINISTIC`, `HWVX_START`, `HWVX_AUTOINPUT`, `HWVX_CARLOG`. Fit to the retail scale and
report the cars that are furthest off and rank inversions, per release.

**Ship.** Retail bars by default. Option "Car stats: Original | Measured" (launcher and/or a recipe field), applied
as a load-time patch of the four bytes from a committed table keyed by car id plus a hash of its physics fields
(a modded car falls back to retail). Visual only: no effect on online or saves.

**Stages.** C1 inventory (`xdlrs cars stats`, the bar curve) · C2 measuring harness · C3 analysis report - **the
user reviews it** · C4 the patch and setting · C5 docs.

## D. Launcher Settings in sections

The Settings page is getting long (8 rows in 0.4, +3-4 in 0.4.1). Split it into sub-tabs along the top of the page
(user's idea; sub-tabs rather than submenus with back buttons: one click away, matches the launcher's main tabs,
left/right switches sections on a pad):

| Section | Settings |
|---|---|
| Display | windowed/fullscreen, PC textures, draw distance, split-screen detail, fonts (B) |
| Audio | stereo, movies |
| Controls | mouse steering, button prompts (A), remap (A6) |
| Game | main menu style, car stats (C) |

Do this first in 0.4.1 (D1, src/port/launcher.c: a sub-tab row, rows per section, the launcher's N-choice rows the
prompts setting needs), so A5/B7/C4 add their rows to a section. Remember the last section; launcher screenshots
per section (`HWVX_LAUNCHER_SHOT`).

## E. Resolution scale (0.5× to 2×)

The port renders into an internal framebuffer (the EFB) at the window's size. A scale sizes the EFB at
0.5×-2× the window and scales it to the window on present: below 1× for weak GPUs, above 1× as supersampling.

- Choices: 0.5×, 0.75×, 1× (default), 1.5×, 2× in the Display section (`graphics.cfg resscale=`,
  `HWVX_RESSCALE`, `--res-scale`).
- Cap at the GPU's maximum texture/render-target size (2× of 4K is 7680×4320); log the cap.
- Downscale from >1× with a proper filter (box/Lanczos) so it actually anti-aliases; upscale from <1× with
  bilinear, nearest as an option. Both SDL_GPU (Metal/D3D12/Vulkan) and OpenGL paths.
- Everything that reads the EFB: the HUD's 4:3 layout and widescreen widening, split-screen viewports, screenshots
  and frame dumps (at the render size: user decision 2026-11-13), the viewer's shared frames and pick coordinates (map through
  the scale), Port_ViewerEfbSize.
- Stages: E1 the scaled EFB and present filter (1× byte-identical: attract demo identical); E2 the setting row and
  overrides; E3 checks at 0.5×/2× on each renderer, a 4K window, split screen, the editor's embedded view.

## Candidate for 0.5 (or 0.4.1 if small): VX2-style handling

The user's Unity fangame ("VX2", a remake of much of HWVX) has its own handling model; port it as another handling
mode (Options → Handling, next to the PC's third mode), off by default. To decide the release: read the C# source
(location from the user) - custom raycast suspension/grip maths port cleanly to C; Unity WheelColliders/PhysX would
have to be re-created on the game's physics (bigger). The game's car model stays authoritative (collisions, damage,
stunts, AI); online needs every player on the same mode (the hello's compatibility check); AI cars keep the
original unless decided; part C's stats per mode.
